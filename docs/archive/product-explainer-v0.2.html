A "self-updating construction whiteboard" shared by humans and agents

The project holds a set of HTML views inside the git repo. Humans check progress, click choices and circle comments on them; agents treat them as the task brief when writing code, then rewrite the views to match what was actually built; a checker makes sure the views and the code agree; and the whole team looks at the same whiteboard through git.

Kid version: You and a robot builder share one whiteboard. On it are a map of the city, the houses being built, and every decision made. You circle a spot and write "put a garden here," and the robot goes and builds it; when it is done, it redraws the whiteboard to the new look. A little inspector compares the whiteboard with the real city every day and lights up red wherever the drawing is wrong. Your friends look at this very same whiteboard too.

How to read: about 8 minutes from top to bottom. Where something is unclear, you can select text on the page and leave an annotation; the last section has a few decision cards that need your call.

1. Today's problem: all you and the agent have is text

Agents already write code quickly; the slow part is the communication between you and them. Both directions are text only: you type what you want into a terminal, and it replies with a big block of summary. But architecture, progress and trade-offs are structured things; forced into text, they are tiring for you to read and easy for the agent to misread.

    First use: you tell the agent "initialize this for me." It reads through the code, generates a small data file in the repo (recording which modules exist and which code each module maps to), and then generates three views: architecture, plan and decisions.
  2. 2
    Open it in the morning: one command opens the whiteboard in the browser, with no app to install and no login. Switch views on the left, read the architecture in the middle, and on the right are the questions the agent left for you overnight.
  3. 3
    Answer with a click: the agent asks "how should a failed payment be retried," and instead of writing a paragraph you click B and then "Confirm."   4. 4
    Circle to make a request: circle the payments module and write "split into two services." That note goes into an inbox, and the agent reads it first the next time it starts work.
  5. 5
    When the agent finishes: it changes the code and also redraws the whiteboard to the new look. The checker automatically compares them: is what the diagram says still in the code? Anything that doesn't match lights up yellow, and one click gets the agent to fix it.

How a team uses it

  • The whiteboard is just ordinary files in the repo, and everyone shares it through git. No server and no accounts needed.
  • In a PR, besides the code changes you can also see "what this PR did to the architecture and the plan."
  • Run the checker in CI: if the code changed but the whiteboard wasn't updated, the PR gets a warning.
  • When a new teammate joins, they open the whiteboard and see an always-current project map and a history of decisions.

3. Why HTML: anything that can be clicked shouldn't make people type

⚡ Faster

To answer the agent's question, one click is enough; no reading a paragraph and then writing one back.

👀 Easier to grasp

Options, trade-offs and recommendations sit side by side, so you can compare at a glance. Architecture and flows read much faster as diagrams than as text.

😌 Less tiring

Cards, color and white space are easier than a screen full of text. When you answer dozens of questions a day, the difference is obvious.

🎯 Answers aren't misunderstood

The option you click becomes a definite piece of data handed to the agent, so it doesn't have to guess what your paragraph meant.

HTML has three more advantages that text lacks: agents write it most fluently; every element on the page can be pointed at precisely, so your annotations don't land in the wrong place; and it is an ordinary file that can go into git, be shared, and be opened in any browser. The page you are reading is itself an example: after you click your answers to the decision cards in Section 7, they go straight back to the agent.

4. Why it failed before and can work now: "the reusable rocket"

Documents, architecture diagrams and specs have always died, for two reasons:

Before

Maintenance took human time, so nobody maintained them, and they went stale before long.

People rarely came back to look, because it was only reference material, not a place to get work done. (CodeSee, a code-map product, shut down in 2024.)

Now

Maintenance cost drops to nearly zero: the agent updates it as a side effect every time it finishes work, and people don't have to lift a finger.

People come back every day: the whiteboard is where you direct the agent and where you do your work, so you come naturally.

This is like the reusable rocket: rockets already existed, and what SpaceX changed was the cost structure of launching. A visual model of a project couldn't be made to work before, not because it was useless but because maintenance was too expensive. Now that maintenance has become cheap, it can work.

5. The product is made of four things

ComponentWhat it does
Data fileA small text file that records which modules, decisions and tasks the project has. Every item carries an anchor pointing to real code, for example "payments module = src/pay/, entry function is charge()." It is the single source of truth.
HTML viewsWritten by the agent, good-looking and interactive. Every element on the page is attached to an item in the data file, so when you click "Payments," payments lights up in every diagram at once.
① viewerOne command opens it in the browser and treats the several views as one workspace. Your clicks and annotations are written to the inbox. The interaction is modeled on lavish.
② skillTeaches the agent to read the data file and the inbox before starting work, and to update the data file and the views when it finishes. Works with Claude Code, Codex and others.
③ CheckerCompares the data file with the code: are the anchors still there? Has the code under an anchor changed? It doesn't use AI, so results are stable and fast, and it can go into CI. AI is only used when fixing things.
④ HooksRuns the checker automatically every time the agent finishes work.
The key technical idea: separate "facts" from "good looks." Facts live in a small data file, with anchors, checkable, and merging normally in git. Good looks are left to HTML, which can be regenerated any time it goes stale. This solves the two problems that stop others: there is no way to check whether HTML is stale, and HTML merges poorly in git.

6. How it differs from others

Many people are heading in this direction, which is exactly a sign the direction is right. The closest to us is Nimbalyst (MIT, about 2.1k stars). I had a subagent read through its code: it does this very well, and in places it is more mature than our original idea.

What Nimbalyst does better than we imagined (to learn from)

  • Documents can embed "decision blocks": 6 question types, multi-person voting, results written straight into the file, and the agent is woken once a decision is made.
  • A formal file-format spec: every item has a permanent ID, types are extensible, and there is an operation log.
  • It can extract "what the human said at the time" from Claude Code session records.
  • A full editor, multiple agents in parallel, and a mobile app.

What it doesn't do and would find hard to change (our opportunity)

  • HTML views are not the main thing, and elements in a view aren't attached to data.
  • Anchors only go as far as "file and line number," not functions or routes.
  • No deterministic check that can go into CI.
  • Team collaboration has to go through its server, not just git and PRs. Its pricing model dictates this, so it is hard to change.
  • To use it, you first have to move into a new desktop app.
The difference in one sentence: Nimbalyst is a new home you move into; we are a transparent membrane laid over how you already work. You still use the terminal, you still use your existing agent, your team still uses git, and you just get a whiteboard that updates itself and doesn't lie. We could also be compatible with the same file format, so users on both sides can interoperate.

7. What the first version does, and the biggest risk

The first version does

  • The data-file format, plus three views: architecture, plan, decisions
  • viewer: browsing, jumping, annotating, decision cards, changing task status
  • skill and hooks: support one agent first
  • Checker: start with file and function anchors for one language
  • Use this tool to develop this tool itself (eat our own dog food)

The first version does not

  • A real-time multi-user collaboration server (teams use git for now)
  • Automatically inferred business flow diagrams (easy to get wrong, and once wrong users stop trusting it)
  • Its own chat agent
  • Drag-and-drop architecture editing
  • Cloud and accounts
The biggest risk is people, not technology: will people actually direct the agent from the whiteboard rather than keep typing in the terminal? You only find out by using it yourself. How to verify: use it yourself for two weeks and record how many times you direct the agent on the whiteboard versus in the terminal. If fewer than 20% happen on the whiteboard, or you stop opening it yourself, stop and rethink.
